클라우드플레어 524 오류 원인과 해결: 100초 제한과 비동기 작업 패턴

2026.09.28 · 베일드 솔루션

관리자 화면에서 리포트 생성 버튼을 눌렀더니 한참 돌다가 "Error 524: A timeout occurred"가 떴습니다. 그런데 서버 로그를 보면 작업은 끝까지 정상으로 끝나 있었습니다. 서버는 일을 다 했는데 사용자는 오류를 본 것입니다. 원인과 구조적인 해결 방법을 정리합니다.

증상

  • 짧은 요청은 멀쩡하고, 오래 걸리는 요청만 정확히 100초 전후에서 끊깁니다.
  • 화면에는 클라우드플레어 로고가 박힌 524 페이지가 뜹니다.
  • 서버 쪽에서는 에러가 없고, 작업 결과도 저장되어 있습니다.
  • 사용자가 다시 누르면 같은 작업이 한 번 더 돌아 중복 결과가 생깁니다.

원인: 프록시가 응답을 100초까지만 기다림

클라우드플레어 프록시를 켜면 방문자의 요청은 클라우드플레어를 거쳐 서버로 갑니다. 클라우드플레어는 서버와 연결을 맺은 뒤 응답이 오기를 기다리는데, 무료와 프로 요금제에서는 이 대기 시간이 100초로 고정되어 있습니다. 그 안에 응답이 시작되지 않으면 연결을 끊고 방문자에게 524를 보여 줍니다.

중요한 점은 서버 쪽 작업은 멈추지 않는다는 것입니다. 클라우드플레어가 끊은 것은 방문자와의 연결일 뿐이고, 서버는 요청을 끝까지 처리합니다. 그래서 "로그는 정상인데 화면은 오류"라는 이상한 상황이 됩니다.

서버의 타임아웃 설정을 아무리 늘려도 해결되지 않습니다. 끊는 주체가 서버가 아니라 앞단 프록시이기 때문입니다. 엔터프라이즈 요금제가 아니라면 이 100초는 바꿀 수 없다고 보고 설계해야 합니다.

확인 방법

  1. 브라우저 개발자 도구의 네트워크 탭에서 실패한 요청의 소요 시간을 봅니다. 100초 근처라면 거의 확실합니다.
  2. 서버 액세스 로그에서 같은 요청의 처리 시간과 상태 코드를 찾습니다. 서버는 200으로 기록했는데 방문자는 524를 받았다면 원인이 맞습니다.
  3. 같은 작업을 입력 범위를 줄여서 실행해 봅니다. 100초 안에 끝나는 크기에서는 정상이라면 시간 문제입니다.

해결: 요청 하나에 다 하지 않는다

오래 걸리는 작업은 요청 하나로 처리하지 말고 세 단계로 나눕니다.

  1. 시작 요청: 서버는 작업을 등록만 하고 작업 번호를 즉시 돌려줍니다. 1초 안에 끝납니다.
  2. 백그라운드 처리: 실제 작업은 요청과 무관하게 서버 안에서 돌고, 진행 상태를 저장합니다.
  3. 상태 조회: 화면은 몇 초마다 작업 번호로 상태를 묻고, 끝나면 결과를 받아 표시합니다.
// 서버 (Node.js 예시)
const jobs = new Map();

app.post('/api/report', (req, res) => {
  const id = crypto.randomUUID();
  jobs.set(id, { status: 'running', startedAt: Date.now() });
  buildReport(req.body)
    .then(result => jobs.set(id, { status: 'done', result }))
    .catch(err => jobs.set(id, { status: 'failed', error: String(err) }));
  res.json({ id });            // 바로 응답
});

app.get('/api/report/:id', (req, res) => {
  res.json(jobs.get(req.params.id) || { status: 'unknown' });
});
// 화면
const { id } = await fetch('/api/report', { method: 'POST', body }).then(r => r.json());
let job;
do {
  await new Promise(r => setTimeout(r, 3000));
  job = await fetch('/api/report/' + id).then(r => r.json());
} while (job.status === 'running');

이렇게 바꾸면 어떤 요청도 몇 초를 넘기지 않으므로 524가 날 수 없습니다. 작업이 10분이 걸려도 상관없습니다.

같이 챙겨야 할 것

  • 중복 실행 막기: 같은 입력으로 이미 돌고 있는 작업이 있으면 새로 만들지 말고 기존 작업 번호를 돌려줍니다. 사용자가 버튼을 여러 번 눌러도 작업은 하나만 돕니다.
  • 상태 저장 위치: 예시처럼 메모리에 두면 서버가 재시작될 때 사라집니다. 운영에서는 데이터베이스나 Redis에 두고, 오래된 작업 기록은 주기적으로 지웁니다.
  • 진행률 표시: 상태에 "30건 중 12건 처리" 같은 진행 정보를 넣어 두면 사용자가 기다릴 이유를 알게 되고, 새로고침으로 중복 요청을 만드는 일이 줄어듭니다.
  • 실패 처리: 백그라운드 작업이 예외로 죽어도 상태는 반드시 failed로 바꿔야 합니다. 그렇지 않으면 화면이 영원히 기다립니다. 상태 조회에 최대 대기 시간도 둡니다.

임시방편과 그 한계

응답을 스트리밍으로 조금씩 보내 연결을 유지하는 방법도 있지만, 중간 계층의 버퍼링 설정에 따라 동작이 달라지고 작업이 길어질수록 불안정합니다. 프록시를 끄고 서버에 직접 연결하는 방법은 클라우드플레어가 주는 보호와 캐시를 전부 잃는 것이라 권하지 않습니다. 오래 걸리는 작업이 하나라도 있다면 처음부터 비동기 구조로 만드는 편이 결국 가장 적게 고칩니다.

정리

  • 524는 서버 오류가 아니라 클라우드플레어가 100초 넘게 응답을 기다리다 끊은 것입니다. 서버 작업은 대개 끝까지 돌아 있습니다.
  • 서버 타임아웃을 늘려서는 해결되지 않습니다.
  • 작업 등록, 백그라운드 처리, 상태 조회로 나누면 작업 길이와 상관없이 해결됩니다. 중복 실행 방지와 실패 상태 처리를 같이 넣습니다.
