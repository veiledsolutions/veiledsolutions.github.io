MySQL 인덱스 타는지 확인하는 법: EXPLAIN 읽기와 복합 인덱스 순서

2026.09.29 · 베일드 솔루션

게시판 목록이 느려서 인덱스를 추가했는데 속도가 그대로였습니다. 확인해 보니 인덱스는 만들어져 있었지만 쿼리가 그 인덱스를 쓰지 않고 있었습니다. 인덱스는 "만들었다"가 아니라 "쿼리가 탄다"까지 확인해야 끝납니다. 그 확인 방법을 정리합니다.

1. 테이블에 어떤 인덱스가 있는지 보기

먼저 현재 인덱스 목록부터 확인합니다.

SHOW INDEX FROM posts;
  • Key_name: 인덱스 이름. 같은 이름이 여러 줄이면 복합 인덱스입니다.
  • Seq_in_index: 복합 인덱스 안에서 컬럼 순서입니다. 뒤에서 설명할 순서 규칙 때문에 이 숫자가 중요합니다.
  • Cardinality: 서로 다른 값의 대략적인 개수. 값 종류가 너무 적은 컬럼(예: 0과 1만 있는 플래그) 단독 인덱스는 효과가 거의 없습니다.

2. EXPLAIN으로 인덱스를 타는지 확인하기

확인하고 싶은 쿼리 앞에 EXPLAIN만 붙이면 됩니다. 쿼리는 실행되지 않고 실행 계획만 나옵니다.

EXPLAIN SELECT id, title, created_at
  FROM posts
 WHERE user_id = 1024 AND is_comment = 0
 ORDER BY id DESC
 LIMIT 20;

결과에서 볼 칸은 네 개입니다.

type: 어떤 방식으로 찾았나

  • const, eq_ref: 기본키나 유니크 키로 한 건을 바로 찾음. 가장 좋습니다.
  • ref: 인덱스로 같은 값을 가진 행들을 찾음. 일반적인 조회에서 목표로 하는 값입니다.
  • range: 인덱스로 범위를 찾음(BETWEEN, >, IN 등). 괜찮습니다.
  • index: 인덱스 전체를 처음부터 끝까지 읽음. 이름과 달리 좋은 신호가 아닙니다.
  • ALL: 테이블 전체를 읽음. 인덱스를 못 타고 있다는 뜻입니다.

key: 실제로 고른 인덱스

possible_keys는 쓸 수 있는 후보이고, key가 옵티마이저가 실제로 고른 인덱스입니다. key가 NULL이면 인덱스를 안 쓴 것입니다. 인덱스를 추가했는데 여기 이름이 안 보이면 그 인덱스는 이 쿼리에 쓸모가 없는 것입니다.

rows: 읽을 것으로 예상한 행 수

결과는 20건인데 rows가 수십만이면, 20건을 얻으려고 수십만 건을 읽는다는 뜻입니다. 인덱스를 고친 뒤 이 숫자가 결과 건수 근처까지 내려오면 제대로 된 것입니다. 추정치라 정확하지 않지만 자릿수는 믿을 만합니다.

Extra: 추가 작업

  • Using index: 테이블까지 가지 않고 인덱스만으로 답을 냈음(커버링 인덱스). 가장 좋습니다.
  • Using where: 읽은 행을 다시 조건으로 걸렀음. 그 자체로 나쁘진 않지만 rows가 크면 문제입니다.
  • Using filesort: 정렬을 인덱스로 못 하고 따로 했음. 목록 쿼리에서 보이면 인덱스 순서를 의심하세요.
  • Using temporary: 임시 테이블을 만들었음. GROUP BY, DISTINCT에서 자주 보이며 무겁습니다.
MySQL 8.0.18 이상이라면 EXPLAIN ANALYZE를 쓰면 예상치가 아니라 실제로 읽은 행 수와 걸린 시간이 나옵니다. 단, 이건 쿼리를 실제로 실행하므로 운영 DB에서 무거운 쿼리에 쓸 때는 주의하세요.

3. 인덱스 추가하고 다시 확인하기

위 쿼리가 type: ALL, rows 수십만, Using filesort로 나왔다고 해 봅시다. 조건 컬럼과 정렬 컬럼을 묶은 복합 인덱스를 만듭니다.

ALTER TABLE posts
  ADD INDEX idx_user_comment_id (user_id, is_comment, id);

EXPLAIN SELECT id, title, created_at
  FROM posts
 WHERE user_id = 1024 AND is_comment = 0
 ORDER BY id DESC
 LIMIT 20;
-- type: ref, key: idx_user_comment_id, rows: 수십, Extra에서 filesort 사라짐

InnoDB는 보조 인덱스 추가를 대부분 온라인으로 처리해서 작업 중에도 읽기와 쓰기가 됩니다. 반면 MyISAM 테이블은 인덱스를 만드는 동안 테이블이 잠기므로, 큰 테이블이라면 접속이 적은 시간에 하세요.

4. 복합 인덱스 컬럼 순서 규칙

복합 인덱스는 전화번호부처럼 왼쪽 컬럼부터 차례대로 정렬되어 있습니다. 그래서 순서가 틀리면 인덱스가 있어도 못 탑니다.

  • 맨 왼쪽 컬럼이 조건에 없으면 못 탑니다. (user_id, is_comment, id) 인덱스는 WHERE is_comment = 0 만으로는 쓰이지 않습니다.
  • 같다(=) 조건 컬럼을 앞에, 정렬 컬럼을 뒤에 둡니다. 그래야 찾은 범위 안에서 이미 정렬된 순서로 읽고 filesort가 사라집니다.
  • 범위 조건 뒤의 컬럼은 활용도가 떨어집니다. (created_at, user_id)에 created_at > ... 범위 조건을 걸면, 그 뒤 user_id는 인덱스로 좁히는 데 거의 못 씁니다. 범위 조건 컬럼은 되도록 뒤에 둡니다.

5. 인덱스를 못 타는 대표 패턴

인덱스가 맞게 있는데도 key가 NULL이면 쿼리 쪽이 인덱스를 막고 있는 경우가 많습니다.

-- 컬럼에 함수를 씌움 → 인덱스 못 탐
WHERE DATE(created_at) = '2026-09-29'
-- 범위로 바꾸면 탐
WHERE created_at >= '2026-09-29' AND created_at < '2026-09-30'

-- 문자열 컬럼에 숫자를 비교 → 형변환 때문에 못 탐
WHERE phone = 01012345678
-- 따옴표로 같은 타입 비교
WHERE phone = '01012345678'

-- 앞쪽 와일드카드 → 못 탐
WHERE title LIKE '%인덱스%'
-- 앞부분 고정이면 탐
WHERE title LIKE '인덱스%'

본문 검색처럼 앞쪽 와일드카드가 꼭 필요하다면 일반 인덱스로는 해결되지 않습니다. MySQL 5.7 이상은 ngram 파서를 쓰는 FULLTEXT 인덱스로 한글 검색을 인덱스 기반으로 바꿀 수 있습니다.

6. 인덱스 힌트는 마지막 수단

옵티마이저가 엉뚱한 인덱스를 고를 때는 힌트로 강제할 수 있습니다.

SELECT id, title FROM posts FORCE INDEX (idx_user_comment_id)
 WHERE user_id = 1024 AND is_comment = 0
 ORDER BY id DESC LIMIT 20;

다만 힌트는 데이터 분포가 바뀌어도 고정되어 나중에 오히려 느려지는 원인이 됩니다. 먼저 ANALYZE TABLE posts;로 통계를 갱신해 보고, 그래도 안 될 때만 쓰는 편이 안전합니다.

7. 필요 없는 인덱스 정리

인덱스는 읽기를 빠르게 하는 대신 쓰기마다 같이 갱신되므로, 안 쓰는 인덱스는 비용만 듭니다. MySQL 8.0에서는 바로 지우지 말고 먼저 보이지 않게 해 두고 지켜보는 방법이 안전합니다.

ALTER TABLE posts ALTER INDEX idx_old INVISIBLE;  -- 옵티마이저가 무시
-- 며칠 지켜보고 문제 없으면
ALTER TABLE posts DROP INDEX idx_old;
-- 문제가 생기면 즉시 되돌리기
ALTER TABLE posts ALTER INDEX idx_old VISIBLE;

정리

  • SHOW INDEX로 현재 인덱스와 컬럼 순서를 확인합니다.
  • EXPLAIN에서 type이 ALL이거나 key가 NULL이면 인덱스를 못 타는 중입니다.
  • rows가 결과 건수에 가까워지고 Using filesort가 사라지면 성공입니다.
  • 복합 인덱스는 같다 조건, 정렬, 범위 순으로 설계합니다.
  • 컬럼에 함수, 형변환, 앞쪽 와일드카드가 있으면 쿼리부터 고칩니다.
  • 힌트는 통계 갱신 뒤에도 안 될 때만 씁니다.
